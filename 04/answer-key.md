# Ключ к домашнему заданию 4

Открывайте после собственной попытки. Это один вариант решения; полные файлы находятся в [self-check](self-check/README.md). Имена ограничений в автоматических пробах соответствуют этому варианту.

## 1. Решения о схеме и выпуске

До исправления диагностический запрос возвращает заказ 1003: он принадлежит организации 10, а его клиент — организации 20. Повторов номера внутри одной организации нет. Номер 42 у двух разных организаций допустим. Простой FK на customer_id пропускает неверную связь, потому что клиент 201 существует.

В [01-protect.sql](self-check/01-protect.sql) добавлены UNIQUE(tenant_id,id) у customers, UNIQUE(tenant_id,order_no) у orders и составной FK(tenant_id,customer_id). FK с NOT VALID сразу проверяет новые INSERT/UPDATE; проверку старых строк можно отложить до исправления заказа 1003. Затем отдельно выполняется VALIDATE. Обе колонки составной ссылки уже обязательны в исходной схеме.

Неверные INSERT/UPDATE дают 23503, дубликат номера внутри организации — 23505. Заказ 43 организации 20 допустим, хотя у организации 10 номер 43 уже есть. Добавление FK с NOT VALID тоже требует DDL-блокировки. Для большой таблицы нужно отдельно спланировать построение уникальных индексов: ADD UNIQUE может выполняться долго.

Если превратить total_cents в сумму в рублях, старое приложение продолжит присылать туда целые копейки. После такого обновления число 60000 будет означать 60000 рублей вместо 600. Поэтому на стадии expand добавлена отдельная колонка. total_cents пока хранит копейки, переходная версия приложения пишет обе суммы.

Подходит numeric(14,4): десять целых и четыре дробных разряда покрывают заданный диапазон, десятичные значения хранятся точно. На финальной стадии колонка должна быть обязательной. Ограничение от нуля до заданной верхней границы также исключает NaN и бесконечности. Float не гарантирует точное представление всех таких значений. Можно выбрать numeric без заданного масштаба и отдельно ограничить диапазон и дробную часть. Если API должен отклонять лишние знаки после запятой, вход нужно проверить до приведения к numeric(14,4), которое округлит значение.

В карточке клиента хранится его текущий email. В выпущенном счёте или записи отправки нужен адрес, на который этот счёт отправляли. При изменении email клиента адрес уже отправленного счёта должен сохраниться.

## 2. Исправление заказа, повтор и ошибка записи аудита

[02-repair.sql](self-check/02-repair.sql) выполняет ту же логику, что описана в [repair-core.sql](self-check/repair-core.sql). Временная функция используется для повторяемых аварийных проб; в своём решении можно написать DO или эквивалентный транзакционный SQL.

Сначала блокируется заказ, затем читается и при наличии блокируется его аудит. Скрипт проверяет значения, прочитанные под блокировкой: с момента диагностического SELECT заказ мог измениться. UPDATE возвращает фактическое новое значение. Оно записывается в аудит в той же транзакции.

| Состояние заказа 1003 и аудита | Действие |
| --- | --- |
| Организация 10, клиент 201, аудита нет | Исправить на 102, записать 201 → 102 / SUP-204 |
| Организация 10, клиент 102, точный аудит SUP-204 уже есть | Завершить повтор без изменения заказа и аудита |
| Клиент 102, аудита нет или он противоречит SUP-204 | Остановиться и проверить историю исправления |
| Клиент 101, другая организация или аудит при старом клиенте | Остановиться и выяснить историю |

Если у заказа уже указан клиент 102, нужен аудит с переходом 201 → 102 по SUP-204. Без него неизвестно, кто и почему изменил заказ. ON CONFLICT DO NOTHING подавит конфликт вставки, но не сравнит содержимое существующего аудита с ожидаемым.

Готовый скрипт ошибки добавляет временный CHECK, который запрещает запись аудита. Первый вызов получает 23514 после попытки UPDATE; вся транзакция откатывается. В новой сессии у заказа 1003 остаётся клиент 201, аудит пуст. После отключения ошибки заказ получает клиента 102 и одну запись аудита. Повтор всего файла сохраняет эту запись, включая repaired_at, и снова успешно выполняет VALIDATE для FK. В repair_audit первичный ключ задан по order_id, поэтому таблица хранит одно исправление на заказ. Для истории нескольких исправлений потребуется изменить эту модель.

## 3. Эксперимент со смешанными версиями

[03-expand.sql](self-check/03-expand.sql) добавляет total_amount с допустимым NULL и без DEFAULT. При DEFAULT 0 заказ с ещё не перенесённой суммой выглядел бы как заказ на ноль рублей. До переключения актуальная сумма хранится в total_cents.

После prepare-mixed.sql получаем:

| id | total_cents | total_amount | Текущая сумма, RUB |
| --- | --- | --- | --- |
| 1001 | 150000 | 1500.0000 | 1500.0000 |
| 1002 | 60000 | 500.0000 | 600.0000 |
| 1003 | 19990 | NULL | 199.9000 |

Чтение total_cents остаётся корректным. COALESCE(total_amount,total_cents::numeric/100) у заказа 1002 вернёт 500 вместо 600: импорт изменил total_cents, а total_amount остался прежним. Перенос с условием WHERE total_amount IS NULL исправит заказ 1003 и пропустит устаревшую сумму у 1002.

```sql
SELECT id, total_cents, total_amount
FROM hw04.orders
WHERE total_amount IS DISTINCT FROM total_cents::numeric / 100;
```

Запрос находит оба расхождения. Приведение к numeric выполняется до деления, иначе целочисленное деление потеряет копейки. Если первоначальный вариант читает total_cents и сверяет все расхождения, эксперимент подтвердит его корректность. В отчёте достаточно объяснить, почему он сработал.

## 4. Переключение и совместимость записей

[04-cutover.sql](self-check/04-cutover.sql) выполняется после остановки всех процессов, которые пишут только total_cents: старого приложения, импорта, фоновых заданий и ручных скриптов. Оставшиеся процессы атомарно меняют обе суммы. Остановку нужно подтвердить отдельно: SQL-сверка показывает состояние данных в момент запроса, старый импорт может изменить их позже.

Финальная сверка обновляет total_amount из total_cents во всех строках с IS DISTINCT FROM. Затем отдельными транзакциями добавляются проверки диапазона, наличия и равенства с NOT VALID, выполняется VALIDATE и устанавливается NOT NULL. После этого чтение переключают на total_amount. Суммы заказов — 1500.0000, 600.0000 и 199.9000.

Запись обеих согласованных сумм проходит. UPDATE только total_cents на другую сумму получает 23514, INSERT без total_amount — 23502. Пара 1 копейка / 0.0125 RUB нарушает равенство представлений: новый тариф пока включать нельзя. Отрицательная сумма и NaN также отвергаются, нулевая согласованная сумма допустима.

На большой таблице перенос идёт порциями по стабильному ключу с отдельными COMMIT. После остановки старых процессов нужна финальная сверка. Если DDL не получает блокировку за lock_timeout, транзакцию откатывают, выясняют, кто удерживает блокировку, и повторяют попытку. Размер порций, нагрузку и длительность блокировок нужно проверить на рабочем объёме данных.

## 5. Возврат старой версии и завершение миграции

[05-rollback.sql](self-check/05-rollback.sql) при остановленной записи снимает NOT NULL и обе временные проверки amount_present и amount_matches_cents. Диапазон новой суммы, составной FK, UNIQUE номера и исходные суммы сохраняются. Если снять только NOT NULL, проверка равенства по-прежнему запретит менять total_cents, пока total_amount содержит прежнюю сумму.

После возврата INSERT старого приложения оставляет total_amount=NULL, а UPDATE только total_cents делает заполненный total_amount устаревшим. Читать сумму снова нужно из total_cents. Перед следующей попыткой миграции придётся проверить приложения и фоновые процессы, обновить total_amount во всех расходящихся строках и восстановить ограничения.

После частичного переноса данных старая версия приложения ещё работает с этой схемой. После переключения вернуть чтение к total_cents можно, пока обе суммы обновляются вместе. Чтобы запустить приложение, которое пишет только total_cents, потребуются изменения из 05-rollback.sql либо адаптер для совместимой записи. Когда появится сумма с дробной копейкой, вернуть старый формат без преобразования данных уже не получится.

Стадию contract проводят отдельным выпуском, когда возврат старой версии больше не требуется и все процессы перестали читать и писать total_cents. Запись приостанавливают, удаляют total_cents и проверку равенства, переводят приложения на обязательный total_amount, сохраняют проверку диапазона и возобновляют работу. После этого можно включить новый тариф. Если выполнялся 05-rollback.sql, перед contract нужно повторить сверку и переключение из 04-cutover.sql.

Например, 0.0125 RUB нельзя точно записать целым числом копеек. При возврате потребуется договориться о преобразовании, округлении или восстановлении данных. Даже если total_cents сохранён, точное значение в него не поместится.
