# ДЗ 7. Ключ для преподавателя

Оценивать нужно контракт и наблюдаемый результат. SQL из self-check — один рабочий вариант. Корректный протокол на языке приложения тоже подходит. Студент не обязан повторять команды управления сервером вручную: они предоставлены, чтобы сосредоточиться на поведении сервиса.

## 1. Read-your-writes, replay и снимок

В R1 r2 остановлена до записи. При ANY 1 и remote_apply primary может закончить COMMIT после применения на r1. Свежий SELECT заказа 1001 на r1 возвращает paid, на r2 — created. Progress 101 также есть только на r1. Настройка требует одного удалённого ответа, но не выбирает читателя для следующего запроса.

Токен получают после успешного COMMIT на writer, например через pg_current_wal_insert_lsn(). Он может включать чужие более поздние записи и тем самым задавать более строгий барьер. Это безопасно для требования «не раньше моего COMMIT». Токен до COMMIT или после INSERT без завершённой транзакции для этого договора не подходит. Объяснение должно различать WAL записи строки и запись COMMIT.

При ANY 2 r1 может уже применить новую транзакцию, пока writer ждёт r2 в SyncRep. Возобновление r2 завершает ожидание. Свежие снимки r1/r2 после ответа writer видят cancelled и progress 102. B на r1 со старым Repeatable Read всё ещё читает paid и не видит 102. Replay не заменяет снимок SQL. R2 следует завершать возвратом replay, а не отменой COMMIT: отмена ожидания синхронного ответа не возвращает уже локально завершённую транзакцию назад.

### Матрица условий

Предполагаются fsync=on, local flush, remote_apply, исправный primary и независимые отказы выбранных получателей. Строка «копии» относится к моменту успешного завершения записи, а не к произвольному следующему моменту после новых отказов.

| Настройка | Минимум копий WAL с primary | Один получатель недоступен | Чтение после ответа |
| --- | --- | --- | --- |
| ANY 1 из 2 | 2 | Запись возможна через оставшегося | Произвольная реплика может отставать |
| ANY 2 из 2 | 3 | Запись ждёт второго | Новый снимок любой из этих двух реплик видит запись |
| ANY 2 из 3 | 3 | Запись возможна через оставшихся двух | Третий узел может отставать; нужен выбранный барьер |

Для N кандидатов, q необходимых ответов и f недоступных получателей условие продолжения записи при работающем primary: N−f≥q. Успешная запись имеет не менее q+1 устойчивых копий WAL. Асинхронная дополнительная реплика не меняет q. Эти настройки сами не реализуют выбор лидера, fencing и безопасный promotion.

### Допустимый клиентский протокол

Пример псевдокода, в котором deadline — абсолютное значение по монотонным часам клиента:

```text
read_order(id, token, deadline):
    проверить принадлежность token текущей истории и допустимому writer
    пока остаётся бюджет и политика допускает ожидание:
        connection = взять соединение выбранного узла в пределах остатка
        начать чистую READ COMMITTED READ ONLY транзакцию
        проверить replay_lsn >= token на этом же узле
        завершить эту транзакцию
        если барьер пройден:
            начать новую READ COMMITTED READ ONLY транзакцию
            прочитать order на том же узле в пределах остатка бюджета
            завершить транзакцию, вернуть ответ
        вернуть чистое соединение и ждать ограниченный интервал
    если разрешён primary и бюджет ещё есть:
        прочитать с текущего writer в новом снимке в пределах остатка
    иначе вернуть freshness_timeout/unavailable
```

Возможен и ранний отказ без ожидания. self-check/01-fence.sql — такой SQL-контроль на физическом standby. Он получает min_lsn/order_id через psql -v, использует новый снимок и при непройденном барьере завершается с кодом 3. Он не является готовым клиентом с общим deadline: statement_timeout ограничивает отдельный SQL, а не ожидание пула, соединение и всю цепочку попыток.

Нужно проверять replay выбранного узла и читать с него же. После проверки нельзя незаметно получить из балансировщика другой сервер. В клиенте учитываются таймаут соединения, ожидание пула, отмена запросов и очистка транзакции. Соединение с неизвестным состоянием не возвращается обычным образом в пул. Старый RR нельзя «освежить» ещё одним SELECT. Токен другой timeline/истории нельзя использовать как универсальный числовой таймер; здесь общая история — явная предпосылка опыта.

У заказа 2002 дата по UTC — 2026-11-02, по America/New_York — 2026-11-01. Явное `(created_at AT TIME ZONE 'UTC')::date` совпадает. Бизнес-день магазина может использовать другой согласованный пояс. Хранимый external_token переносится как значение; SELECT gen_random_uuid() создаёт новое значение при выполнении запроса. Эти различия возможны без лага.

## 2. Исправление логической проекции

### L1: поток прошёл дальше пропущенной операции

После missing источник содержит 1001=paid, а subscriber не содержит 1001. Метка 1101 применена. В PostgreSQL 18 missing UPDATE пропускается, счётчик confl_update_missing растёт. Повторный сон не синтезирует исходную строку.

Перед исправлением нужно определить владельца данных и исключить конкурирующие изменения во время сверки. В данном контракте это publisher. Выгрузка primary через snapshot содержит JSON всех его колонок. self-check/02-missing.sql загружает её во временную таблицу и вставляет недостающий 1001. External_token сохраняется, receipt_token создаётся заново: удалённый локальный token источник не хранит. Для прочих существующих строк local token сохраняется.

Одного исходного состояния для общей системы недостаточно: при продолжающейся записи нужен согласованный snapshot/поток либо другой протокол сверки. В задании writers на окно сверки/исправления остановлены явно.

### L2: весь набор изменений транзакции

Локальный 1201=draft занимает PK. INSERT источника вызывает insert_exists/23505; применение повторяет транзакцию до устранения конфликта. 1202 тоже пока отсутствует, progress 1203 не применён. Недостаточно проверить только конфликтующий id.

В этом опыте локальная draft ошибочна, publisher владеет общими данными, но receipt_token остаётся локальным полем. На окно исправления закрываем чтение повреждённых ключей. self-check/02-conflict.sql сначала сохраняет token в локальной таблице receipt_repair и только затем удаляет ошибочную строку в той же транзакции. После повтора apply получаем 1201=paid, 1202=created и метку 1203. Отдельный 02-conflict-finish.sql проверяет применение всей транзакции, возвращает сохранённый token и убирает запись ремонта. Перед открытием чтения сверяем общие и локальные поля. При падении процесса сохранённая таблица позволяет продолжить исправление. Реальное исправление также учитывает локальные связи и владельцев записи.

SKIP пропускает транзакцию целиком. Здесь он потеряет и 1202, который сам по себе не конфликтовал. Пересоздание slot/подписки без плана исходного snapshot и изменений тоже не является автоматическим исправлением. Глобальная очистка проекции уничтожит локальные поля и требует отдельного протокола повторной синхронизации.

### L3: отдельная схема

Добавление currency на publisher не выполняет ALTER на subscriber. Новый INSERT не применится, пока совместимая колонка отсутствует. В данном примере у всех старых и новых строк валюта RUB, поэтому добавление `currency text NOT NULL DEFAULT 'RUB'` на получателе согласует и схему, и данные. После этого доходят 1301 и 1302.

Для совместимого добавления сначала готовят subscriber, затем writer. Промежуточные версии приложения должны работать с обеими схемами. В другом случае DEFAULT на получателе может быть неверным заполнением исторических данных; выпуск требует собственного backfill и сверки. Сравнение JSON после L3 должно включать currency, иначе эту колонку можно пропустить незаметно.

### L4: FK и побочные эффекты

Publisher имеет tenant 99, subscriber — нет. Apply worker работает с session_replication_role=replica, поэтому обычный FK-триггер не проверяет вставку. Заказ 1401 и progress 1402 появляются, а anti-join orders/tenants на subscriber находит отсутствующего родителя. Обычный локальный INSERT с tenant 99 до исправления даёт 23503.

В опыте справочник также принадлежит источнику: недостающий tenant можно перенести и затем выбрать постоянный способ его доставки. Например, согласовать публикацию связанных таблиц в одном потоке и подготовку схемы. Простое выполнение VALIDATE CONSTRAINT для уже валидного ограничения не является надёжной повторной сверкой всех строк. Anti-join проверяет нужную связь явно.

Обычный audit trigger на subscriber тоже не срабатывает при apply, но локальные исправления его вызывают. REPLICA и ALWAYS меняют это поведение. Нельзя включать ALWAYS для всех триггеров: исходный outbox, аудит или внешнее действие могут выполниться повторно. Отдельно определяются владелец эффекта и ключ дедупликации. UNIQUE и CHECK продолжают проверять применяемые данные и способны остановить поток.

### Полная сверка и генератор

self-check/02-reconcile.sql сравнивает source JSON с `to_jsonb(subscriber_row)-'receipt_token'` через FULL JOIN по id. Это находит missing, extra и different. Отдельный anti-join находит отсутствующих tenants. Время выгружается и читается в UTC, чтобы формат одной и той же временной величины не создавал ложный JSON diff. При разных правилах представления потребуется типизированная нормализация значений.

После всех исправлений ожидается пустой diff общих колонок и пустой anti-join. Дополнительный хороший контроль: локально изменить одну общую колонку и создать лишнюю строку, увидеть обе ошибки сверкой, затем вернуть состояние. Равное количество строк такой контроль не заменяет.

Generated_ids содержит 1 и 2. Первый следующий номер primary — 3, первого вызова свежей sequence subscriber — 1. Сам вызов nextval уже потребляет номер; повторное наблюдение не является тем же состоянием. До переноса writer: остановить старую запись, догнать поток, исключить параллельный nextval, подготовить генератор и только затем включить новую запись. В непустой таблице с обычной sequence один вариант:

```sql
SELECT setval('hw07.generated_ids_id_seq',
              (SELECT max(id) FROM hw07.generated_ids), true);
```

Следующий nextval будет max+1. Для пустой таблицы, нестандартного increment, общего пространства ключей нескольких writers или внешних выделенных диапазонов нужен другой согласованный вариант. Setval сам по себе не fencing старого writer.

## 3. PITR без потери корректной поздней работы

В физической копии четыре заказа. На hw07_before_delete уже присутствует 3001 и его позиция, но ещё нет DELETE. Поэтому restored содержит пять заказов, три из них tenant 42. Заказ 2001 там ещё paid, 3002 отсутствует. Его наличие на primary и актуальный cancelled у 2001 относятся к более поздней корректной работе.

Проверки перед переносом: целостность базовой копии, достижение нужного restore point и paused replay, наличие ожидаемых строк/связей/сумм и возможность прочитать их. Pg_verifybackup проверяет файлы копии, а не весь прикладной результат восстановления; для него нужны отдельные SELECT.

Полная замена primary этим снимком вернёт удалённые строки, но потеряет 3002 и отмену 2001. В контракте требуется выборочный перенос. Restored остаётся отдельным источником чтения, действующая база не заменяется.

### Вариант атомарного исправления

self-check/03-repair.sql загружает обе CSV во временные таблицы и в одной транзакции:

1. Берёт SHARE ROW EXCLUSIVE на orders и order_items. Это совместимо с обычным SELECT и блокирует конкурирующий DML; согласованная остановка writers остаётся частью плана.
2. Вставляет только отсутствующие заказы tenant 42, сохраняя их исходные поля. ON CONFLICT DO NOTHING не перезаписывает текущие строки.
3. Сохраняет RETURNING id вставленных заказов во временном наборе.
4. Вставляет позиции **только этих новых заказов**. Иначе можно вернуть законно удалённую позднее позицию уже существующего заказа.
5. Выполняет COMMIT. Ошибка вставки позиции откатывает и ранее вставленные заказы.

Первый запуск даёт 3 orders и 3 items, повтор — 0 и 0. Итог: шесть заказов 1001, 1002, 2001, 2002, 3001, 3002; шесть позиций; суммы совпадают. Статус 2001 остаётся cancelled, 3002 — paid. При повторе все существующие строки и их external_token должны остаться теми же.

Если повреждённый заказ уже существует в другой версии или была корректная бизнес-отмена после удаления, нужно разбирать его отдельно по истории операций. Здесь этих неоднозначностей нет: набор удалённых строк и разрешённое исправление заданы. «Вставить всё отсутствующее» без этого контекста не является универсальным восстановлением.

Архив и копия в одном volume не переживают потерю этого volume. Опыт не измеряет сетевое разделение, отказ диска, fencing, production RTO или реальное переключение клиентов. RPO зависит от доступной цепочки копий/WAL и границы требуемых данных; RTO включает обнаружение, выбор цели, восстановление, прикладную сверку и возврат сервиса. Эти зависимости студент должен назвать без вымышленных замеров.

## Дополнительный блок

Пулы приложения: 12×20=240 клиентских соединений. Серверные пулы: 2×3×15=90 backend без reserve pool и иных подключений. Это разные границы. Нужен общий бюджет с миграциями, администрированием, rolling deployment и перегруппировкой нагрузки при отказе. HTTP внутри BEGIN продлевает владение backend. Tenant_id устанавливается доверенным кодом через SET LOCAL внутри каждой транзакции, после проверки доступа; сам GUC не является аутентификацией.

Для октября полуоткрытый диапазон по occurred_at от 2026-10-01+00 до 2026-11-01+00 исключает сентябрь и ноябрь. Date_trunc над ключом в исходном запросе может оставить все секции. Сравниваются одинаковые результаты, планы и buffers, а не только время. Составной PK допускает тот же event_id на другой дате. Пример глобального правила — обычная таблица event_registry(event_id PRIMARY KEY) и атомарная запись реестра и события одной транзакцией. Повтор с тем же id должен иметь согласованные параметры/ответ; случайный UUID не добавляет уникальное ограничение на event_id partitioned parent.

## Проверка и оценка

4 балла за чтение: реальные R1/R2, правильная граница токена/снимка, явная ветка deadline и обоснованная матрица. 3 за проекцию: все L1–L4, целая транзакция, полная сверка, локальные поля и sequence. 3 за восстановление: правильная цель, выборочный атомарный перенос, текущие данные и повтор.

При дефекте результата соответствующий блок возвращается на исправление. Красивый отчёт, совпадение имён с эталоном и малое время выполнения не компенсируют устаревшее чтение, потерю строки или перезапись корректной работы. Дополнительная часть полезна для обсуждения, но не заменяет основной контракт.
