# Разбор после собственной попытки

Читайте вместе с [ключом](../answer-key.md). Эталон — один из допустимых протоколов, имена и реализация могут отличаться.

01-fence.sql — SQL-проверка выбранного standby с новым снимком и ранним отказом. Передайте min_lsn и order_id через -v. Он не реализует ожидание пула или общий deadline приложения: это остаётся в вашей политике.

После L1 выгрузите актуальный source-orders.csv и примените 02-missing.sql к subscriber. После L2 закройте чтение повреждённых ключей, примените 02-conflict.sql, дождитесь всех трёх ожидаемых результатов и выполните 02-conflict-finish.sql: он вернёт прежний receipt_token. После итоговой сверки откройте чтение. Затем L3/02-ddl.sql и L4/02-fk.sql. Фикстуры и DDL-исправления запускаются один раз на своей стадии. 02-reconcile.sql читает новую выгрузку источника и выводит различия и отсутствующих родителей.

После PITR сохраните обе recovered-выгрузки из restored. Примените 03-repair.sql к primary: первый запуск возвращает 3 orders и 3 items, повтор — 0 и 0. Сам SQL не выбирает, какие бизнес-изменения разрешено возвращать: это задано контрактом именно этого происшествия.

Пример применения эталона:

```sh
docker compose exec -T lab sh /work/lab/control.sh psql primary -f /work/self-check/03-repair.sql
```

Все скрипты меняют только выбранную базу текущего Compose project. Сохраните свои решения до сравнения с эталоном.
