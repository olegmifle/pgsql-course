# ДЗ 5. Разбор решений

Откройте этот файл после выполнения задания. Ниже разобраны два набора индексов: какие запросы они обслуживают, как ведут себя после обновлений и сколько работы добавляют при записи. Другие решения оцениваются по тем же проверкам результатов и измерениям.

## Два набора индексов

В [наборе A](self-check/01-lean.sql) ленту обслуживает B-tree (store_id, created_at DESC, id DESC). Для очереди создан отдельный индекс (store_id, created_at, id) WHERE status='pending'. Равенство по магазину ограничивает участок дерева, порядок времени и id позволяет остановить чтение после LIMIT строк. id также задаёт однозначную границу страницы для заказов с одинаковым временем.

В [наборе B](self-check/02-cover.sql) к ключу ленты добавлены INCLUDE(status, total_amount), а для очереди используется полный ключ (store_id, status, created_at, id). На таблице после VACUUM покрывающий индекс может обслужить ленту без обращений к heap. Второй индекс поддерживает поиск и по другим статусам. Оба индекса занимают больше места, чем соответствующие индексы A, а изменение суммы требует обновлять INCLUDE. Поля INCLUDE доступны для выдачи результата; поиск и порядок определяются ключевыми колонками. Возможность обойтись без heap зависит также от видимости страниц.

В обоих наборах есть индекс lower(email), GIN(metadata) и BRIN(occurred_at). В своём решении можно оставить последовательное чтение для отдельного запроса, если дополнительный индекс обходится дороже полученного выигрыша. Исходный orders_store_idx удалён: новые B-tree начинаются со store_id и поддерживают поиск по магазину. Перед таким удалением в рабочей базе нужно проверить остальные запросы к таблице, их планы и размеры индексов.

A и B применяются по отдельности в исходных базах. A хранит в индексе очереди только pending-заказы и использует более узкий индекс ленты. B даёт покрытие ленты и поиск по любому статусу. Сравните оба магазина: для магазина 1 нужно обработать гораздо больше исходных строк, чем для магазина 42. Итоговый выбор зависит от того, насколько выигрыш чтения оправдывает место и обслуживание записи.

## Пагинация и обновления

[Пример keyset](self-check/keyset.sql) сохраняет фильтр периода и использует условие (created_at, id) < (cursor_time, cursor_id) с прежним ORDER BY DESC. На неизменных данных он возвращает те же 20 строк в том же порядке, что OFFSET 5000. В учебном файле контрольный курсор получается через OFFSET; в API последняя пара приходит с предыдущей страницы. Для перехода сразу к произвольному номеру страницы одного такого курсора недостаточно.

В данных есть группы заказов с одинаковым временем. Граница после первой страницы проходит внутри группы, поэтому условие только created_at < cursor_time пропустит оставшийся заказ с тем же временем. При этом запрос всё равно может вернуть 20 строк. Проверка должна сравнивать сами строки и порядок со следующей страницей исходного запроса. Конкурентное изменение ключей сортировки или состава выборки может смещать страницы и при использовании курсора; для чтения из единого снимка потребуются соответствующие транзакции или поддержка со стороны API.

[Синхронизация](fixtures/01-busy-orders.sql) обновляет payload; значения исходных SELECT сохраняются. Сравните Heap Fetches и buffers до обновления, после него и после VACUUM. Index Only Scan использует visibility map: для страницы без признака all-visible видимость строки проверяется через heap. После UPDATE таких проверок может стать больше, а VACUUM позволяет восстановить признак all-visible. На число обращений влияют состояние страниц и момент обслуживания. Heap Fetches выводится для Index Only Scan; обычный Index Scan обращается к heap и без этой строки в плане. Подробнее — в [документации PostgreSQL](https://www.postgresql.org/docs/18/indexes-index-only-scans.html).

## Выражения и JSONB

QE ищет по lower(email), поэтому в примере индексируется это выражение. В результате возвращается исходный email с сохранением регистра. Замена проекции на lower(email) изменит результат. Если для решения нужна другая колляция или проверка уникальности, это следует согласовать с требованиями к хранению email.

QJ поддерживают GIN с jsonb_path_ops и jsonb_ops. Для оператора ? в QC подходит стандартный jsonb_ops. В примерах один стандартный GIN обслуживает оба запроса. Два специализированных индекса либо индексы по выражениям и подмножествам таблицы тоже можно сравнить по размеру и цене чтения и записи. Поддерживаемые операторы перечислены в [документации JSONB](https://www.postgresql.org/docs/18/datatype-json.html#JSON-INDEXING).

В исходных данных у 9677 заказов есть ключ coupon; в 967 случаях его значение — JSON null. Условие metadata ? 'coupon' включает эти строки. Условие metadata->>'coupon' IS NOT NULL возвращает 8710 строк, поэтому такая замена QC потеряет часть результата. Проверить различие можно запросом:

```sql
SELECT count(*) FILTER (WHERE metadata ? 'coupon') AS present,
       count(*) FILTER (WHERE metadata @> '{"coupon":null}'::jsonb) AS json_null,
       count(*) FILTER (WHERE metadata->>'coupon' IS NOT NULL) AS text_nonnull
FROM hw05.orders;
```

При выборе индекса для JSONB учитывайте операторы и частоту запросов. Для поиска одного фиксированного значения индекс по выражению или подмножеству может оказаться дешевле общего GIN.

## Журнал событий

Первоначальный QT возвращает 3600. BRIN хранит сводки диапазонов физических страниц. По ним выбираются диапазоны, в которых могут находиться нужные события, затем строки проверяются в heap. В исходной таблице соседние страницы содержат события с близким временем. Параметр pages_per_range определяет размер диапазона: от него зависят объём индекса и точность отбора страниц.

[Поздняя доставка](fixtures/02-late-events.sql) добавляет 50000 исторических событий в конец heap. В новых диапазонах min/max охватывают широкий период. Диапазоны без сводок тоже включаются в проверку. Сравните count, lossy blocks, Rows Removed by Index Recheck и buffers до и после brin_summarize_new_values. После суммирования страницы остаются в прежнем порядке, поэтому min/max новых диапазонов могут оставаться широкими. По фактическому плану определите, сколько страниц BRIN всё ещё позволяет пропустить. [Описание BRIN](https://www.postgresql.org/docs/18/brin.html).

VACUUM/ANALYZE и суммирование BRIN выполняют разные операции. При сравнении решений можно менять pages_per_range, использовать B-tree или оставлять последовательное чтение, учитывая размер индекса и запись. После доставки точный count нужно вычислить на новых данных.

## Цена записи и установка индексов

[Измерение записи](fixtures/03-write-cost.sql) выполняет 2500 INSERT и 500 UPDATE суммы pending-заказов. Подготовка, чтение и изменения должны идти в одинаковом порядке для обоих наборов. Сравнивайте корневой WAL каждого EXPLAIN; работа дочерних узлов уже учтена в родительском. После ROLLBACK видимые значения восстанавливаются, а выполненная работа со страницами и WAL остаётся. Для сопоставимого повторения нужна свежая база.

В A сумма не входит в индекс. При наличии места на странице и соблюдении остальных условий изменение суммы может использовать HOT. В B total_amount включён в B-tree через INCLUDE, поэтому изменение суммы требует обслуживания индекса и исключает HOT для такого обновления. Учитывайте также свободное место, версии строк и остальные индексы. По этому опыту можно сравнить WAL и время указанных операций; производительность при конкурентной нагрузке требует отдельного измерения. [Условия HOT](https://www.postgresql.org/docs/18/storage-hot.html).

[Пример установки](self-check/03-rollout.sql) создаёт один индекс через CREATE INDEX CONCURRENTLY вне BEGIN, показывает indisready/indisvalid и удаляет старый индекс после проверки. Его нужно выполнять в отдельной исходной базе. Для установки всего набора A или B аналогично опишите операции с каждым индексом. CONCURRENTLY допускает обычную запись, выполняет дополнительные проходы и может ждать другие транзакции. После ошибки может остаться INVALID-индекс: проверьте его состояние, устраните причину и выберите удаление или перестроение. IF NOT EXISTS проверяет наличие имени; определение и валидность существующего индекса проверяются отдельно.

В сценарии укажите порядок создания, проверку определений и валидности, планы обоих магазинов, условия удаления старых индексов и действия при ошибке. Учтите свободное место, WAL, ожидания и нагрузку во время построения. При удалении индекса сохраняйте ограничения целостности, которые он обеспечивает. На учебном стенде можно проверить последовательность команд; длительность и нагрузку на большой таблице нужно оценивать отдельно. [CONCURRENTLY и ограничения](https://www.postgresql.org/docs/18/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY).
