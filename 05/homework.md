# Домашнее задание 5. Индексы сервиса заказов

Сервис обслуживает несколько интернет-магазинов. Операторы просматривают ленту заказов и исправляют суммы, обработчик забирает заказы из очереди pending, синхронизация обновляет служебные данные. Поддержка ищет покупателей и промокоды, аналитика считает события за выбранный период.

Спроектируйте два набора индексов, сравните чтение и запись, выберите один набор и подготовьте его установку в работающей базе. Ориентировочное время после запуска среды — 4–6 часов для мидла и 2–3 часа для сеньора.

Схема, данные и команды запуска находятся в [пакете](README.md). Записывайте решения в SQL-заготовки. [Ключ](answer-key.md) и self-check открывайте после выполнения задания.

## Данные и запросы

В hw05.orders хранятся 300000 заказов: 150000 у магазина 1 и около 1500 у магазина 42. Несколько заказов могут иметь одинаковое время создания. У большинства статус paid, небольшая часть находится в очереди pending. В отдельных таблицах — 100000 покупателей и 600000 событий, первоначально записанных по времени. Данные сгенерированы для задания; результаты замеров относятся к этому стенду.

| Запрос | Требуемый результат |
| --- | --- |
| QF1 / QF42 | Последние 20 заказов магазина с начала указанного периода. Колонки id, created_at, status, total_amount. Порядок created_at DESC, id DESC |
| QW1 / QW42 | До 20 самых старых pending-заказов магазина. Колонки id, created_at. Порядок created_at, id |
| QPAGE | Страница ленты магазина 1 с LIMIT 20 OFFSET 5000. Фильтр, колонки и порядок как у QF |
| QE | id и email покупателя по lower(email). Регистр исходного email сохраняется |
| QJ | id заказов с JSONB segment=vip через containment. Порядок не задан |
| QC | id заказов с ключом coupon верхнего уровня, включая coupon с JSON null. Порядок не задан |
| QT | Точное число событий за полуоткрытый часовой интервал |

Исходные SELECT находятся в [queries.sql](queries.sql). При оптимизации сохраняйте колонки, типы, значения, число повторений строк и указанный порядок. Можно переписывать SQL и менять способ передачи параметров из приложения. PK и остальные правила целостности должны сохраниться. Если дополнительный индекс для запроса не нужен, подтвердите это замерами.

## 1. Сравнить два набора индексов

Перед созданием индексов запишите ожидаемый эффект каждого из них. Основной набор A сохраните в [01-indexes.sql](01-indexes.sql), альтернативный B — в [02-alternative.sql](02-alternative.sql). Укажите, для каких запросов или операций B может быть выгоднее A и во что обойдётся этот выигрыш. Применяйте каждый набор в отдельной свежей базе с одинаковыми исходными данными. Ограничений на число индексов, их размер или buffers нет.

Сравните QF/QW для обоих магазинов, а также QE/QJ/QC/QT. Для каждого индекса объясните выбор колонок, предиката или выражения и перечислите запросы, которые он обслуживает. Проверьте, нужен ли исходный индекс по store_id после добавления новых. Покажите хотя бы одно различие между наборами в скорости чтения, покрытии, размере, наборе поддерживаемых запросов или стоимости записи.

Сохраните полные результаты и планы до и после создания индексов. [comparison.sql](comparison.sql) применяет выбранный файл DDL и сравнивает значения, дубли и порядок строк. Если переписываете SELECT, измените соответствующий AFTER-блок. Скрипт проверяет корректность; ускорение проверяйте по планам и замерам.

Для каждого запроса сделайте один запуск для прогрева и три измерения. Сравните медиану времени и число обработанных блоков. Значения buffers у родительского узла уже включают работу дочерних, поэтому повторно складывать их не нужно. Зафиксируйте окружение и настройки, чтобы сравнение можно было повторить.

## 2. Проверить пагинацию и чтение после обновлений

В [keyset.sql](keyset.sql) реализуйте чтение QPAGE по границе предыдущей страницы. В файле уже есть получение контрольного курсора через OFFSET. В API курсор приходит с предыдущей страницы, поэтому время его подготовки в учебном файле учитывайте отдельно от чтения следующей страницы.

Сверьте все строки страницы и их порядок с исходным OFFSET на неизменных данных. Проверьте также переход после первой страницы: заказы с одинаковым временем должны попадать на соседние страницы без пропусков и дублей. Объясните, как переход к курсору меняет возможность выбора произвольного номера страницы и что произойдёт при конкурентном изменении данных.

После исходных замеров один раз выполните [синхронизацию заказов](fixtures/01-busy-orders.sql). Она обновляет служебный payload с COMMIT; значения исходных SELECT сохраняются. До ручного VACUUM повторите QF/QW и сравните обращения к heap и buffers для A/B. Затем выполните VACUUM (ANALYZE) hw05.orders и повторите чтение. Объясните изменения в планах и решите, какие поля стоит включать в покрывающий индекс при частых обновлениях заказов. Используйте фактические значения Heap Fetches из своих планов.

## 3. Подобрать индексы для JSONB и журнала событий

QE/QJ/QC входят в оба набора из первого задания. Проверьте соответствие индексов выражениям и операторам этих запросов. Напишите SQL-проверку, которая различает отсутствие coupon и присутствующий coupon с JSON null. Если переписываете JSONB-запрос, сравните его полный результат с исходным.

Для QT объясните, как выбранный индекс зависит от физического порядка событий. После исходного измерения один раз выполните [доставку поздних событий](fixtures/02-late-events.sql): в конец таблицы добавятся 50000 событий с историческим временем. Повторите QT, проверьте точный count на новых данных и выполните необходимое обслуживание индекса. Если используете BRIN, сравните также план после обновления сводок.

Сопоставьте число кандидатов, recheck и обращения к heap с исходным замером. Объясните, почему индекс стал обрабатывать больше или меньше страниц. После добавления событий ожидаемое число строк вычисляется заново.

## 4. Оценить запись и подготовить установку индексов

В конце опыта с каждым набором выполните [измерение INSERT/UPDATE/WAL](fixtures/03-write-cost.sql). Скрипт вставляет 2500 заказов, исправляет суммы 500 pending-заказов и выполняет ROLLBACK. После отката видимые значения восстанавливаются, а уже выполненная работа со страницами и WAL остаётся. Для повторного сравнения используйте свежую базу.

Подготовка и последовательность изменений для A/B должны совпадать. Сравните размеры индексов, время, buffers и WAL для INSERT и UPDATE. Объясните, как индексируемые поля влияют на HOT и обслуживание индексов. Выводы о цене записи ограничьте выполненными операциями: стенд не измеряет пропускную способность сервиса при конкурентной нагрузке.

Выберите итоговый набор и укажите, при каких требованиях или изменениях нагрузки предпочли бы альтернативу. В [03-rollout.sql](03-rollout.sql) запишите порядок создания и проверки индексов на работающей таблице, условия удаления старых и действия при ошибке построения. Учитывайте транзакционные границы, ожидания и валидность индекса. На стенде постройте хотя бы один индекс способом, допускающим обычную запись во время построения, и проверьте его состояние. Время этой операции на большой таблице потребует отдельной оценки.

## Сдача и оценка

Заполните [шаблон отчёта](report-template.md) и сохраните как report.md. Сдайте 01-indexes.sql, 02-alternative.sql, keyset.sql, checks.sql, 03-rollout.sql, report.md и выбранные планы и результаты из results/. Свои проверки корректности и запросы для измерений сохраните в [checks.sql](checks.sql). В отчёте ссылайтесь на соответствующие планы и результаты.

| Критерий | Баллы |
| --- | --- |
| Два обоснованных набора, оба магазина и полный результат | 3 |
| Пагинация с одинаковым временем, поведение после UPDATE | 2 |
| Операторы JSONB, отсутствующий/JSON-null coupon, поздние события | 2 |
| Цена INSERT/UPDATE, выбор набора и порядок установки индексов | 3 |

Для 8–10 баллов нужны проверки и обоснования по всем четырём разделам. Если часть проверок или объяснений отсутствует, оценка снижается. Ошибки в результатах сначала исправляются, затем оценивается производительность. Имена индексов, планы и миллисекунды могут отличаться от ключа. Время выполнения задания на оценку не влияет.
