# Урок 7. Реплика, восстановление, пул соединений и секции

Четыре опыта используют один контейнер: primary на 5540, replica на 5541, восстановленную копию на 5542 и PgBouncer на 5543. Это внутренние порты контейнера; на компьютер они не публикуются. Python-сценарий управляет реальными подключениями и останавливается перед очередным действием.

## Подготовка

Нужен Python 3.10+ стандартной библиотеки. Из этой папки выполните:

```sh
docker compose up -d --build --wait
```

Образ собирается с PgBouncer. При запуске создаются primary, две исходные строки orders, 32 760 events в трёх месячных секциях, базовая резервная копия и физическая реплика. Готовность включает создание копий, поэтому первый запуск может занять время.

Далее запускайте команды по одной из этой же папки. Перед Enter прочитайте SQL, который сценарий печатает, и предположите результат. `show/` содержит те же SQL-фрагменты для чтения в редакторе.

## 1. Чтение после записи на реплике

```sh
python3 run.py replica
```

Сценарий начинает с двух заказов, дожидается реплики и временно приостанавливает **применение WAL**. Затем создаёт заказ 42 на primary и читает его с двух серверов.

Ожидается: primary находит одну строку, replica — ноль. После возобновления replay и ожидания нужного LSN replica тоже находит строку. Файлы: `show/01_insert_order.sql`, `02_read_order.sql`.

Подтверждённая запись на primary не гарантирует немедленное read-after-write на асинхронной реплике. Задержка здесь создана управляемо; нулевая выдача не означает потерю подтверждённой записи. Replay возвращается в рабочее состояние при нормальном завершении и при обычной ошибке сценария.

## 2. PITR после ошибочного DELETE

```sh
python3 run.py restore
```

Перед DELETE сценарий обеспечивает наличие заказов 1, 2, 42 и создаёт уникальную именованную точку восстановления. После удаления primary и replica показывают 0 заказов. Затем из базовой копии и архивного WAL создаётся отдельный сервер, остановленный на выбранной точке.

Ожидается: в восстановленной копии снова **1, 2, 42**, `pg_is_in_recovery() = t`; в текущих primary/replica удаление остаётся. Файлы: `show/03_restore_point.sql`–`05_restored_orders.sql`, механизм восстановления — `restore.sh`.

Реплика применяет ошибочное удаление вместе с правильными записями. Возврат к прошлому состоянию требует пригодной базовой копии, доступного WAL и проверенного восстановления. Опыт восстанавливает отдельную копию; перевод её в роль рабочего primary здесь не выполняется.

## 3. Контекст клиента в transaction pooling

```sh
python3 run.py pool
```

PgBouncer настроен на `pool_mode=transaction` и один backend. Клиент A задаёт tenant 42 через обычный SET; следующий клиент B получает тот же backend и может унаследовать 42. Затем B устанавливает 7 через SET LOCAL внутри своей транзакции.

Ожидается: одинаковый backend PID; A = 42; B до исправления = 42; B с локальным контекстом = 7. Сценарий отдельно проверяет очистку локального контекста после COMMIT. Файлы: `show/06_session_context.sql`–`08_local_context.sql`.

При transaction pooling соединение клиента не закрепляет серверную сессию на весь срок. Нужный контекст задают для каждой транзакции и не полагаются на оставшееся состояние другого клиента.

## 4. Partition pruning

```sh
python3 run.py partitions
```

Сравните `show/09_range.sql` и `10_wrapped_key.sql`: полуоткрытый диапазон непосредственно по `occurred_at` и выбор того же месяца через функцию от ключа.

Ожидается: прямой диапазон читает только `events_2026_10`, вариант с функцией затрагивает три секции. В октябре 11 160 событий. Смотрите список relations и работу в EXPLAIN, затем время. Разбиение таблицы помогает, когда условие позволяет исключить ненужные секции; само наличие секций этого не гарантирует.

## Повтор и дополнительные команды

Каждый опыт можно повторять; один процесс сценария должен закончиться перед следующим. Все четыре подряд, с остановками:

```sh
python3 run.py all
```

Без остановок: `python3 run.py all --auto`. Дополнительный `--report results/run.json` сохраняет результаты самопроверки локально; каталог `results/` исключён из Git. Финальная строка об успешном завершении появляется после встроенных проверок.

Для ручного подключения к primary:

```sh
docker compose exec lab psql -X -h 127.0.0.1 -p 5540 -U course -d course_lesson07
```

На replica используйте 5541, на восстановленной копии после опыта 2 — 5542. Для PgBouncer — 5543 и база `orders`. Скрипт по умолчанию использует проект `postgres-live-students-07`. Если запускаете Compose с собственным `-p`, передайте то же имя через `LESSON07_PROJECT` команде Python.

Остановка: `docker compose down`. **Данные и архив этого стенда находятся в контейнере и удаляются вместе с ним.** Следующий `up` создаёт всё заново. Если сценарий был принудительно оборван и состояние неизвестно, выполните `down`, затем подготовку заново.
