# Урок 6. Конкурентные транзакции

Научимся воспроизводить расписания A/B: запрет грязного чтения, различия RC/RR, write skew, Serializable с полным повтором и резерв последнего товара. Нужны два постоянных подключения.

## Подготовка

Из этой папки выполните:

```sh
docker compose up -d --wait
docker compose exec -T postgres psql -X -U course -d course_live06 -v ON_ERROR_STOP=1 -f /work/setup.sql
```

В двух терминалах откройте:

```sh
docker compose exec postgres psql -X -U course -d course_live06
```

В первом `psql` выполните `\i /work/00-A.sql`, во втором — `\i /work/00-B.sql`. Файлы задают search_path, имена сессий, таймауты и вывод SQLSTATE. Шаги выполняются сразу, без дополнительного Enter перед SQL. Читайте файл до запуска. Ожидаемые ошибки не закрывают интерактивный psql.

Далее `A: файл` означает в окне A выполнить `\i /work/файл`. Каждый список — **строгий порядок** переключений. Перед reset оба окна должны завершить прежние транзакции. При ошибке выполните `ROLLBACK;`.

## 1. Чужое неподтверждённое изменение

1. A: `01-dirty/reset.sql`.
2. A: `01-dirty/A1.sql` — меняет остаток на 0 без COMMIT.
3. B: `01-dirty/B1.sql` — видит 1.
4. A: `01-dirty/A2.sql` — ROLLBACK.
5. B: `01-dirty/B2.sql` — снова 1, затем COMMIT.

PostgreSQL предотвращает грязное чтение. Здесь его не получают, а наблюдают защиту от него. Read Uncommitted в PostgreSQL работает как Read Committed.

## 2. Повторное чтение строки: RC и RR

1. A: `02-read/reset.sql`.
2. A: `02-read/A1-rc.sql` — первое чтение 1.
3. B: `02-read/B1.sql` — записывает 0 в autocommit.
4. A: `02-read/A2.sql` — второе чтение 0, COMMIT.

Повторите все четыре шага, заменив **только** `A1-rc.sql` на `A1-rr.sql`. Получатся 1 и 1. В RC новая команда получает новый снимок; в RR сохраняется снимок первого содержательного оператора.

## 3. Повтор выборки по условию

1. A: `03-phantom/reset.sql` — четыре активных резерва организации 7.
2. A: `03-phantom/A1-rc.sql` — `{1,2,3,4}`, count 4.
3. B: `03-phantom/B1.sql` — добавляет пятый резерв в autocommit.
4. A: `03-phantom/A2.sql` — `{1,2,3,4,5}`, count 5, COMMIT.

Повторите с reset и `A1-rr.sql`: второе чтение по-прежнему даёт четыре строки. После COMMIT A выполните в A `03-phantom/check.sql`: актуальный набор содержит пять. PostgreSQL RR предотвращает изменение множества между такими чтениями, но этого недостаточно для любого межстрочного правила.

## 4. Write skew: оба врача ушли

Правило: в смене должен остаться хотя бы один врач. UPDATE разрешает уход, только если транзакция видит больше одного активного врача.

1. A: `04-skew/reset.sql`.
2. A: `04-skew/A1-rr.sql` — видит двух.
3. B: `04-skew/B1-rr.sql` — тоже видит двух до записи A.
4. A: `04-skew/A2.sql` — меняет врача 1, COMMIT.
5. B: `04-skew/B2.sql` — по прежнему снимку меняет врача 2.
6. B: `04-skew/B3.sql` — COMMIT.
7. A: `04-skew/check.sql` — `on_call=0`, `rule_ok=f`.

Обе проверки были выполнены, записи разных строк не затёрли друг друга, но результат не соответствует ни одному последовательному порядку этих операций. Это write skew — аномалия сериализации.

## 5. Serializable и полный повтор

Повторите шаги 1–5 предыдущего опыта с **A1-ser.sql и B1-ser.sql в обоих окнах**. После успешного COMMIT A продолжение B должно получить `40001`. Если B2 ещё не вернула ошибку, выполните B3: отказ возможен и на COMMIT.

После `40001` в B выполните `\i /work/00-rollback.sql`; если ошибка была на COMMIT, транзакция уже завершилась, повторный ROLLBACK может дать предупреждение. Затем:

1. A: `04-skew/check.sql` — один врач остался, правило выполнено.
2. B: `04-skew/B-retry.sql` — **новая транзакция целиком**; видит одного, UPDATE меняет 0 строк.
3. A: `04-skew/check.sql` — по-прежнему один врач.

Дополнительно после A1-ser и до A2 можно в A выполнить `04-skew/si-read.sql` и увидеть `SIReadLock`. Эта отметка участвует в отслеживании зависимостей SSI; она не равна обычной блокировке строки с ожиданием. При других расписаниях нельзя заранее обещать конкретную жертву или оператор отказа.

## 6. Небезопасный резерв

1. A: `05-reserve/reset.sql`.
2. A: `05-reserve/A1.sql` — читает остаток 1.
3. B: `05-reserve/B1.sql` — тоже читает 1.
4. A: `05-reserve/A2.sql` — подтверждает первый резерв и остаток 0.
5. B: `05-reserve/B2.sql` — подтверждает второй резерв по прежнему решению.
6. A: `05-reserve/check.sql` — остаток 0, зарезервировано 2, `rule_ok=f`.

CHECK остатка `>=0` не выражает правило «остаток + резервы = исходный товар».

## 7. Условная запись

1. A: `06-safe/reset.sql`.
2. A: `06-safe/A1.sql` — `UPDATE … WHERE available>=1 RETURNING …` возвращает одну строку с остатком 0.
3. A: `06-safe/A2.sql` — создаёт резерв **в той же открытой транзакции**.
4. B: `06-safe/B1.sql` — UPDATE ждёт; приглашение пока не возвращается.
5. A: `06-safe/observer.sql` — видны ожидание B и блокер.
6. A: `06-safe/A3.sql` — COMMIT.
7. Дождитесь результата B: UPDATE возвращает **0 строк**.
8. B: `06-safe/B2.sql` — ROLLBACK, без INSERT резерва.
9. A: `06-safe/check.sql` — остаток 0, резерв 1, `rule_ok=t`.

В RC после ожидания условие UPDATE проверяется на актуальной версии строки. Приложение должно проверить число изменённых строк; резерв создают только при успешном списании и внутри той же транзакции.

## Повтор и завершение

Каждый опыт повторяется со своего reset при завершённых транзакциях A/B. При таймауте выполните ROLLBACK в обоих окнах и повторите опыт. Полный `setup.sql` пересоздаёт схему `live06`; перед ним закройте прежние подключения. Не перезапускайте setup посреди расписания.

Выход — `\q` в обоих окнах, остановка — `docker compose down`. Том сохраняется.
