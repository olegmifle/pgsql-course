# Урок 8. Три расследования

Измерим работу за конкретное окно, найдём причину ожидания и проверим, почему VACUUM не может убрать старые версии. Нужны три постоянных подключения A/B/O и обычный терминал для логов.

## Подготовка

Из этой папки выполните:

```sh
docker compose up -d --wait
docker compose exec -T postgres psql -X -U course -d course08 -v ON_ERROR_STOP=1 -f /work/setup.sql
```

Setup пересоздаёт схему `incident08`: 120 000 orders и 20 000 events. Загружается `pg_stat_statements`, включены учебные настройки логирования. Только для events отключён autovacuum, чтобы опыт с удержанным снимком повторялся.

В трёх терминалах откройте:

```sh
docker compose exec postgres psql -X -U course -d course08
```

В первом psql выполните `\i /work/live/00-A.sql`, во втором — `\i /work/live/00-B.sql`, в третьем — `\i /work/live/00-O.sql`. Приглашения подписаны A/B/O. Обозначение `A: файл` ниже означает `\i /work/live/файл` в A. Сохраняйте эти подключения между шагами.

## 1. Найти дорогую работу за окно

| Шаг | Окно | Файл | Что проверить |
| --- | --- | --- | --- |
| 1 | O | `01-window-start.sql` | Начальные счётчики и контекст сбросов |
| 2 | B | `02-workload.sql` | 12 чтений ленты и 80 точечных чтений |
| 3 | O | `03-window-end.sql` | Конечные счётчики |
| 4 | O | `04-delta.sql` | Разности calls, времени и buffers; отдельно несопоставимые записи |
| 5 | O | `05-before.sql` | План ленты: scan, filter, sort и buffers |
| 6 | O | `06-fix.sql` | Частичный индекс под pending нужного tenant и порядок выдачи |
| 7 | O | `07-after.sql` | Те же 20 строк с меньшей работой |
| 8 | O/B/O | Повторите 1–4 | Новое окно той же нагрузки: снова 12 и 80 вызовов |

Не закрывайте O: снимки хранятся во временных таблицах этого подключения. Семейства запросов сравниваются по ключу с `userid` и `toplevel`. При сбросе или изменении записи статистики сравнение может быть недостоверным — такая строка вынесена отдельно, а отсутствие счётчика не подменяется нулём.

Сначала определите лидера по calls, затем по суммарному времени. Это могут быть разные запросы. В EXPLAIN проверьте лишние сканы, фильтрацию и сортировку. После индекса сравните buffers и результат, затем время. Накопленная статистика за всю жизнь записи не заменяет дельту за окно инцидента.

## 2. Блокер и cancel

1. A: `10-A-hold.sql` — UPDATE заказа 42 без завершения транзакции.
2. B: `11-B-wait.sql` — UPDATE того же заказа ждёт; приглашение пока не возвращается.
3. O: `12-blockers.sql` — B находится в active/Lock, A — idle in transaction.
4. O: `13-cancel-idle.sql` — отправляет cancel **собственной учебной A**.
5. O: повторите `12-blockers.sql` — ожидание остаётся.
6. A: `14-A-release.sql` — ROLLBACK освобождает ресурс.
7. Дождитесь возвращения B; B: `15-B-commit.sql`.
8. O: `12-blockers.sql` — рёбер этого ожидания больше нет.

`pg_cancel_backend` отменяет выполняемый запрос. Значение true подтверждает отправку сигнала, а не завершение простаивающей транзакции. Наблюдение нужно повторить после вмешательства. Не вводите следующий файл в B, пока она ещё ждёт.

## 3. Дедлок и его история

После завершения предыдущих транзакций:

1. A: `16-A-deadlock-first.sql` — захватывает заказ 42.
2. B: `17-B-deadlock-first.sql` — захватывает заказ 43.
3. A: `18-A-deadlock-second.sql` — просит 43 и ждёт.
4. B: `19-B-deadlock-second.sql` — просит 42 и замыкает цикл.
5. Дождитесь разрешения дедлока. Одна попытка получает **SQLSTATE `40P01`**. В обоих окнах выполните `ROLLBACK;`.

В обычном терминале из этой папки:

```sh
docker compose logs --since 5m postgres
```

Найдите событие по времени, PID, session ID и `application_name`. Конкретная жертва заранее не гарантируется. В activity цикл уже может отсутствовать: PostgreSQL разорвал его сам. Согласованный порядок захвата ресурсов устраняет причину; изменение `deadlock_timeout` лишь меняет задержку обнаружения.

## 4. Старый снимок удерживает версии

Убедитесь, что A/B сделали ROLLBACK после дедлока.

| Шаг | Окно | Файл | Наблюдение |
| --- | --- | --- | --- |
| 1 | A | `20-A-snapshot.sql` | RR read only, 20 000 событий, снимок установлен |
| 2 | B | `21-B-delete.sql` | Удалены чётные ID, в новом чтении 10 000 |
| 3 | A | `24-A-old.sql` | По старому снимку всё ещё 20 000 |
| 4 | O | `22-vacuum.sql` | VACUUM завершён, но 10 000 версий пока нельзя удалить |
| 5 | O | `23-horizon.sql` | `backend_xmin` A, возраст транзакции и размер heap |
| 6 | A | `24-A-old.sql` | Старый результат сохраняется и после VACUUM |
| 7 | A | `25-A-commit.sql` | Снимок освобождён |
| 8 | O | Снова `22-vacuum.sql`, затем `23-horizon.sql` | Теперь старые версии можно удалить |

VACUUM выполняется вне BEGIN. Он не вправе удалять версии, которые ещё требуются снимку A. `TRUNCATE FALSE` исключает обрезание файла: после очистки размер heap может остаться прежним, а место доступно повторному использованию. `n_dead_tup` — оценка, её точное значение не служит единственным доказательством.

## Отчёт наблюдателя

В обычном терминале:

```sh
docker compose exec -T postgres psql -X -U monitor -d course08 -v ON_ERROR_STOP=1 -f /work/health/health.sql
```

Отчёт показывает контекст, активность, блокеров, накопленный топ запросов, обслуживание, горизонты удержания и настройки логов. Роль monitor имеет `pg_monitor` и read-only режим; она не создаёт временные снимки окна и не получает право сигнализировать чужим сессиям. Задержка приложения, очередь PgBouncer и метрики ОС в этот SQL-отчёт не входят.

## Повтор и завершение

При `25P02` найдите первую ошибку и выполните ROLLBACK. После таймаута завершите обе учебные транзакции и повторите текущий опыт.

Для полного повтора закройте все A/B/O через `\q`, снова выполните `setup.sql` из команды подготовки и откройте подключения заново. Это удалит учебные изменения, восстановит events и уберёт созданный индекс. Статистика всего сервера не сбрасывается: используйте новые окна. Повторный DELETE уже очищенных данных не воспроизводит исходный опыт.

Остановка: `docker compose down`; том сохраняется.
