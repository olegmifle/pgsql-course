# Урок 4. Витрина, которая потеряла операцию

Проверим модель асинхронного отчёта: почему курсор `id > last_id` может пропустить подтверждённую операцию и как хранение факта применения помогает восстановлению и повтору. Два конкурирующих подключения моделируются через `dblink`, поэтому вам нужен один `psql`.

## Подготовка

Из этой папки выполните:

```sh
docker compose up -d --wait
docker compose exec -T postgres psql -X -U course -d course_lesson04 -v ON_ERROR_STOP=1 -f /work/live/core/00_prepare.sql
docker compose exec postgres psql -X -U course -d course_lesson04
```

Подготовка пересоздаёт учебные схемы `live04_projection` и `live04_projection_evidence`. Её повторяют только перед новым полным опытом, после закрытия предыдущего подключения. База должна называться `course_lesson04`: это проверяется самим SQL.

SQL модели лежит в `live/show/`, управляющие сценарии — в `live/core/`. Не выполняйте все `show/` подряд: некоторые фрагменты повторяются в определённых состояниях.

## 1. Воспроизвести потерю

Внутри `psql`:

```sql
\set pause_demo on
\i /work/live/core/01_opening.sql
```

На остановках нажимайте Enter после изучения текущего результата. Сначала прочитайте `live/show/01_source_schema.sql`, `02_old_projection.sql` и `03_old_batch.sql`.

Последовательность опыта:

1. A получает меньший ID операции на 100 рублей и оставляет транзакцию открытой.
2. B получает следующий ID на 200 рублей и подтверждается раньше A.
3. Обработчик видит только B: итог становится 200, курсор уходит вперёд.
4. A подтверждается. Повтор прежнего обработчика уже не находит её ниже курсора.

Итог: **в журнале 300 рублей, в отчёте 200**, хотя выше курсора новых строк нет. ID задаёт порядок выделения номеров, а порядок COMMIT может быть другим. Одна атомарная запись суммы и курсора этого предположения не исправляет.

## 2. Восстановить модель и проверить повтор

В том же подключении:

```sql
\i /work/live/core/02_redesign.sql
```

Читайте по ходу `live/show/05_new_projection.sql`, `06_apply_batch.sql`, `07_rebuild.sql` и `10_compare_switch.sql`. Новая модель хранит отметку: конкретная операция применена к конкретному поколению витрины. Изменение суммы и отметка входят в одну транзакцию.

На остановках проверьте:

- Новое поколение восстанавливает 300 рублей из исходного журнала.
- Повторный конкурентный опыт A2/B2 даёт сначала 500, после позднего COMMIT A2 — 600.
- Внутри отменённого пакета сумма 600; после ROLLBACK опять 500; после повторной обработки 600.
- Ещё один повтор применяет 0 операций. Старый отчёт остаётся на 500, новый совпадает с журналом: 600.
- Перед переключением чтения проверяются полнота и суммы, затем публикуется новое поколение.

Уникальность отметок защищает от повторного применения. Откат суммы вместе с отметкой позволяет заново обработать отменённый пакет. Неверный итог старой витрины не используется как источник восстановления.

## Самопроверка и границы

Объясните, чем поколение витрины отличается от последнего обработанного ID и почему успешная обработка одного пакета ещё не доказывает полноту копии. Какие ошибки появятся, если сумму и отметку фиксировать раздельно?

В этом примере операции неизменяемы, исправления — новые строки; суммы заданы целыми копейками, бизнес-день определён при приёме. Размер пакета ограничен 100 операциями. Индекс отметок, поиск неприменённых операций и хранение истории имеют цену. Опыт проверяет известные пути записи, а не обнаруживает произвольные внешние импорты.

## Повтор и завершение

Закройте `psql` через `\q`, чтобы закрылись и удалённые подключения с незавершёнными транзакциями. Снова выполните команду подготовки, откройте новое подключение и пройдите оба сценария. Подготовку посередине опыта не запускайте.

Для выполнения без остановок оставьте переменную `pause_demo` **неопределённой** в новом psql: не задавайте даже `off`, поскольку здесь проверяется наличие переменной. В текущем подключении её можно удалить через `\unset pause_demo`.

Остановка: `docker compose down`; том сохраняется.
